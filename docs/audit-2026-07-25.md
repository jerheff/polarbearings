# Polarbearings — Project Audit Report

_Date: 2026-07-25 · Method: full read of all 17 `src/polarbearings/` modules plus tooling
(pyproject/justfile/workflows/benchmarks), full test suite run (705 passed, Polars 1.43.0), and
timed repros for every falsifiable performance/behaviour claim below. Follows up on
[audit-2026-07-05.md](audit-2026-07-05.md) and [audit-2026-06-21.md](audit-2026-06-21.md); their
findings are not re-reported._

## Verdict

**Overall health: A− / Very healthy.** The numerical core is careful and well defended — the
overflow cast in the Mann-Whitney AUC, `max == min` instead of `var() == 0` for the tie test, the
stable `log(cosh)` identity, the hand-built inverted-CDF quantile so `d2_pinball_score` matches
scikit-learn exactly, and the version-independent SplitMix64 in `split.py` are all the sort of
detail most metric libraries get wrong. Test infrastructure (100% branch gate via a two-version
coverage combine, `filterwarnings = ["error"]`, `lowest-direct` floor resolution, random test
ordering, a Polars compat sweep) is well above typical pre-1.0 hygiene.

The findings below are **one significant performance finding** and **two API/semantics gaps**. None
of them produce a wrong metric value.

## Findings (prioritized)

### 1. HIGH — Eager `df.select([...])` performs no common-subexpression elimination, so the library's headline composability claim is documented, benchmarked, and demonstrated on the *slow* path

- **Location:** [README.md:53–56](../README.md), [benchmarks/bench_multi_metric.py:1–16](../benchmarks/bench_multi_metric.py), and every `bench_*.py` (all eager `df.select`).
- **Claim under test:** README — *"bundle every metric into a single `df.select([...])`; Polars
  shares the column scans and parallelizes across the independent outputs."* The benchmark
  docstring repeats it: *"lets Polars parallelize across the independent output expressions and
  share the column scans / common subexpressions."*
- **Reality:** CSE is a *lazy-plan optimization*. It does not run on `DataFrame.select`. Every
  threshold metric independently rebuilds the same four `_confusion_components` aggregations, so an
  eager suite pays them once per metric. `LazyFrame.select(...).collect()` deduplicates them — the
  plan shows `__POLARS_CSER_*` nodes — and returns bit-identical results.
- **Measured** (n = 10M, Polars 1.43.0, 3 runs on fresh frames, results asserted identical):

  | Suite | eager `df.select` | lazy `.collect()` | ratio |
  |---|---:|---:|---:|
  | 8 threshold metrics (precision…cohens_kappa) | 0.78 s | 0.031 s | **25x** |
  | 12-metric benchmark suite (the headline number) | 3.40 s | 1.94 s | **1.75x** |
  | roc_auc + log_loss + brier (no shared subexpressions) | 0.51 s | 0.47 s | 1.1x (control) |

  The control row confirms this is specifically redundant recomputation of shared confusion cells,
  not a general eager/lazy overhead.
- **Impact:** Two-sided. (a) Users following the README leave up to 25x on the table on exactly the
  workload the README sells. (b) The published **"13 metrics in one select: 5.8x vs scikit-learn"**
  understates the library — the same suite on the lazy path is ~1.75x faster again, i.e. ~10x.
  Eager `df.select` also scales *linearly* in the number of threshold metrics (62 → 132 → 279 ms for
  2 → 4 → 8 metrics at n=5M) while lazy is nearly flat (10 → 16 → 20 ms), so the gap widens as the
  suite grows.
- **Recommendation:** Make the lazy path the documented one. Add a `polarbearings_one_select_lazy`
  case to `bench_multi_metric.py`, quote the lazy number as the headline in README/PERFORMANCE.md,
  and say plainly in the "Why Polarbearings" bullet that subexpression sharing requires
  `df.lazy().select([...]).collect()`. No source change needed — this is a docs/benchmark fix for
  a real, measured win the library already earns but does not claim.

### 2. MEDIUM — Hyper-parameterized metrics omit their hyper-parameter from the output alias, so sweeping it in one `select` raises `DuplicateError`

- **Location:** [regression.py:19–22](../src/polarbearings/regression.py) (`_regression_alias`),
  [calibration.py:~300](../src/polarbearings/calibration.py) (`_calibration_alias`),
  [ranking.py:~85](../src/polarbearings/ranking.py) (`_ranking_alias`).
- **Impact:** Every one of these fails at plan time:

  ```python
  reg.select([mean_pinball_loss("y", "p", alpha=0.1),      # DuplicateError:
              mean_pinball_loss("y", "p", alpha=0.9)])     # 'mean_pinball_loss_y_p'
  ```

  Confirmed for `mean_pinball_loss(alpha=)`, `d2_pinball_score(alpha=)`,
  `mean_tweedie_deviance(power=)`, `huber_loss(delta=)`, `expected_calibration_error(n_bins=)`,
  `maximum_calibration_error(n_bins=)`, and `dcg_score`/`ndcg_score(log_base=)`. The affected cases
  are the *natural* uses of these metrics — a quantile-loss sweep across alphas, a Tweedie power
  comparison, an ECE bin-count sensitivity check.
- **Precedent already in the codebase:** `fbeta_score` does it correctly —
  `_alias(f"fbeta_{beta:g}", ...)` yields `fbeta_1_y_p_0.5` / `fbeta_2_y_p_0.5`. `ndcg_score` also
  already encodes `k` but not `log_base`. So the convention exists; it just was not applied to the
  regression and calibration families.
- **Note:** The July audit's item 8 flagged the *weight-expression* alias collision (two different
  weight exprs both collapsing to `_w`) as rare. This is the same class of bug but hits a common
  workflow, not a rare one.
- **Recommendation:** Follow the `fbeta` precedent — append the discriminating hyper-parameter to
  the alias when it differs from the default (`_a0.9`, `_p1.5`, `_d2`, `_b20`), keeping current
  names unchanged at defaults so no existing column name moves.

### 3. LOW/MEDIUM — `roc_auc` / `average_precision` / `log_loss` / `brier_score` silently return a one-vs-rest number on a multiclass target, where scikit-learn raises

- **Location:** [roc_auc.py:18](../src/polarbearings/roc_auc.py) and the other probabilistic
  metrics' `pos_label` docstrings.
- **Impact:** On a 3-class target with the default `pos_label=1`, `roc_auc` returns a plausible
  number (0.5 on the repro) while `sklearn.metrics.roc_auc_score` raises
  `ValueError: multi_class must be in ('ovo', 'ovr')`. The one-vs-rest semantics are *deliberate*
  and correctly documented for the classification family (`_confusion_components`: *"every other
  value is treated as negative (one-vs-rest)"*), but the probabilistic metrics only say
  *"Value in `target` treated as the positive class"* — which does not tell a reader what happens
  to the values that are neither.
- **Recommendation:** Docs, not behaviour. Add the same one-vs-rest sentence to the `pos_label`
  docs of the probabilistic family, and note the divergence from scikit-learn's raise in the
  Notes block — this library already documents its scikit-learn divergences elsewhere
  (`jaccard_score`, `ndcg_score`), so this is filling a gap in an established practice.

### 4. LOW — `bootstrap`'s default `n_resamples=200` is an undocumented performance cliff, and bootstrapping `roc_auc` silently switches it to the ~5x slower weighted algorithm

- **Location:** [bootstrap.py](../src/polarbearings/bootstrap.py) (`bootstrap`, `bootstrap_ci`).
- **Measured** (n = 1M, Polars 1.43.0): plain `roc_auc` = 96 ms; bootstrap replicates cost ~470 ms
  each and scale linearly (B=25 → 12.1 s, B=50 → 23.1 s, B=100 → 47.1 s). The default B=200 is
  therefore **~95 s for one metric on 1M rows**, peak RSS ~1.2 GB.
- **Why 5x per replicate:** a replicate passes `weight=`, which routes `roc_auc` off the fast
  unweighted Mann-Whitney rank path onto `_roc_auc_weighted`'s sort + cum_sum + backward_fill
  trapezoidal path. That is *correct* — a Bayesian bootstrap needs continuous weights — but it is
  invisible to the caller, who sees a 200x-work default on top of a 5x-costlier kernel.
- **Scaling is linear, not super-linear** — no pathology, and the `_bootstrap_ci_by` two-step
  already avoids the documented Polars 1.42 memory blowup. This is purely a "the default is
  expensive and nothing says so" issue.
- **Recommendation:** Note the cost model in the `bootstrap`/`bootstrap_ci` docstrings (roughly
  `B x weighted-metric-cost`, and that weighting itself may change the metric's kernel), and
  suggest a smaller `n_resamples` for exploratory work on large frames.

## Positive observations

- **Test suite is genuinely green and fast.** 705 tests pass in 112 s on Polars 1.43.0.
- **Numerical edge cases are handled with unusual care.** The `UInt64` cast before
  `total_pos * total_neg` (silent UInt32 overflow past ~131k rows), `max == min` rather than
  `var() == 0` for the all-ties AUC branch (variance underflows for tiny-magnitude distinct
  scores), the stable `|e| + log1p(exp(-2|e|)) - log 2` log-cosh, and the explicit inverted-CDF
  baseline quantile in `d2_pinball_score` are all correct fixes to bugs that ship in other libraries.
- **The `guarded` / `row_has_missing` null policy is a real contract,** consistently applied, with a
  deliberate and documented split: scalar metrics null the whole result, curves drop incomplete rows.
- **`split.py` rebuilding SplitMix64 out of defined wrapping-`UInt64` arithmetic** rather than
  trusting `Expr.hash` (which Polars explicitly does not promise stable) is the right call, and
  directly closes the July audit's HIGH finding.
- **Benchmarking methodology is honest** — the README names where the library is at parity or
  *slower* than NumPy, which is rare and worth keeping.
